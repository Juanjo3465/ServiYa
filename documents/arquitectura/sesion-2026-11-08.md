## 2. Discusión de arquitectura

A partir de ahí se discutió qué microservicio extraer y cómo preparar el monolito:

1. **Primera recomendación:** extraer `metrics-service` (hoja, consumidor de eventos, roadmap §7.4).
2. **Alternativa propuesta por el usuario:** un orchestrator entre módulos que luego sea el
   controlador de un service mesh.
3. **Conclusión:** un orchestrator central no resuelve el problema real (acoplamiento de datos y
   transacciones cruzadas) y puede convertirse en un “god object”/monolito distribuido. El service
   mesh es infraestructura, no orquestación de negocio.
4. **Camino elegido:** definir **APIs públicas entre módulos** y **enforzarlas con ArchUnit**,
   empezando por mover las fronteras, no por extraer un servicio.

Se midió el acoplamiento actual:

- **43 archivos** con dependencias cruzadas fuera de una API pública.
- **14 archivos** con acceso a `infrastructure` o `application.ports.output` ajenos.
- **30 ciclos** entre módulos.
- `profiles ↔ services` es un clúster duro; `admin` es el ápice/orquestador; `reports` es un read-hub.

## 3. Paso 1 — ArchUnit y baseline congelado

### 3.1 Dependencia

Se añadió a `backend/serviya/pom.xml`:

```xml
<dependency>
  <groupId>com.tngtech.archunit</groupId>
  <artifactId>archunit-junit5</artifactId>
  <version>1.4.1</version>
  <scope>test</scope>
</dependency>
```

**Decisión técnica:** ArchUnit **1.4.1**, no 1.5.1. La 1.5.1 requiere JUnit Platform 1.14.x,
mientras Spring Boot 3.5.5 gestiona 1.12.2; con 1.5.1 el engine de ArchUnit descubría 0 tests.

### 3.2 Test de fronteras

Archivo: `backend/serviya/src/test/java/com/parosurvivors/serviya/architecture/ModuleBoundaryTest.java`

7 reglas:

1. Ningún módulo importa `infrastructure` de otro.
2. Ningún módulo importa `application.ports.output` de otro.
3. Ningún módulo importa `domain` de otro.
4. `shared` no depende de módulos de negocio.
5. Los paquetes `.api` solo dependen de JDK/Spring, del propio `.api` y de `shared.contract`.
6. `domain` no depende de `application`/`infrastructure`.
7. `application` no depende de `infrastructure`.

Las reglas con deuda existente usan `FreezingArchRule` y un baseline en:

```text
backend/serviya/src/test/resources/archunit.properties
backend/serviya/src/test/resources/archunit_store/
```

`allowStoreCreation=false` y `allowStoreUpdate=false` por defecto. Para actualizar
intencionalmente:

```bash
cd backend/serviya
./mvnw test -Darchunit.freeze.store.default.allowStoreUpdate=true
```

### 3.3 Verificación de enforcement

Se añadió temporalmente `admin/BoundaryProbe.java` con una dependencia a
`users.infrastructure.security.JwtService`. El test falló como se esperaba:

```text
modulesMustNotDependOnForeignInfrastructure <<< FAILURE!
Field admin.BoundaryProbe.jwtService has type users.infrastructure.security.JwtService
```

El probe se eliminó y la suite volvió a verde.

### 3.4 Nota sobre ciclos

La regla `slices().should().beFreeOfCycles()` se descartó **temporalmente** porque ArchUnit genera
las violaciones de ciclos con orden/conjunto no determinista; `FreezingArchRule` no puede
estabilizarla (se observaron 36, 49 y 69 ciclos entre ejecuciones idénticas). Se pospuso a un test
determinista de matriz de dependencias.

## 10. Decisiones y justificaciones

1. **ArchUnit 1.4.1**, no 1.5.1, por compatibilidad con JUnit Platform 1.12.2 de Spring Boot.
2. **FreezingArchRule** para adoptar las reglas sin un big-bang refactor.
3. **APIs como `<módulo>.api` + fachada en `<módulo>.application.api`**, sin mover todavía los
   puertos internos.
4. **Strings para enums que cruzan fronteras** (estado, rol, tipo de perfil, tipo de reporte) y
   **boolean para tags**; contratos JSON-friendly para una futura extracción.
5. **APIs solo con datos propios del módulo.** Las vistas compuestas (`ServiceDetail`,
   perfil público con rating) quedan fuera y se componen en el consumidor/BFF.
6. **`OffererProfileSummarySnapshot` sin `averageRating`**; lo aporta `metrics.api`.
7. **Batch lookups** (`findProfiles`, `findByIds`) para evitar N+1.
8. **`config` es la raíz de composición**; puede cablear cualquier módulo.
9. **`admin` no publica API**: es consumidor/orquestador.
10. **Ciclos de módulos**: regla pospuesta por no determinismo de ArchUnit; se hará con matriz de
    dependencias determinista.
